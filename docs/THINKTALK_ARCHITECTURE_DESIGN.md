## 1. 项目整体架构概述

### 1.1 架构类型

**微服务架构** — 基于 **go-zero** 框架构建, 采用 **REST API 网关 + gRPC 领域服务 + MQ 异步消费者** 三层服务模型。

### 1.3 核心设计思想

| 设计原则         | 说明                                                                          |
| ------------ | --------------------------------------------------------------------------- |
| **领域驱动拆分**   | 每个微服务对应一个业务领域 (用户/内容/社交/互动/通知/标签), 服务间通过 gRPC 通信, 数据通过数据库隔离                 |
| **CQRS 模式**  | 写操作通过 Kafka 异步投递, MQ 消费者负责真正落库; 读操作直接查询 MySQL/Redis/ES, 读写路径分离              |
| **两级缓存策略**   | Redis Sorted Set 作为一级缓存 (热点数据), MySQL 为二级存储; 使用 singleflight 防止缓存击穿, 后台异步回填 |
| **CDC 事件驱动** | Canal 监听 MySQL binlog, 将数据变更实时推送至 Kafka, 驱动 ES 索引更新和跨服务计数同步                 |
| **统一错误体系**   | `xcode` 包定义标准错误码, 通过 gRPC 拦截器在服务边界自动转换, REST 层通过 `ErrHandler` 统一序列化为 JSON   |
| **全链路可观测**   | 所有持久化客户端 (GORM / ES / gRPC) 均内置 OpenTelemetry 链路追踪 + Prometheus 指标采集        |

### 1.4 模块解耦原则

- **数据库隔离**: 每个领域服务独占一个 MySQL 数据库, 不允许跨服务直连其他服务的数据库
- **接口契约**: 服务间仅通过 `.proto` 定义的 gRPC 接口通信, 不共享任何数据模型或 ORM 实体
- **异步解耦**: 非关键路径 (点赞计数同步、ES 索引、通知生成) 统一通过 Kafka 异步处理, 主流程不感知
- **配置集中**: 每个服务维护独立的 `etc/*.yaml` 配置文件, 通过 etcd 实现服务发现, 不硬编码任何服务地址

### 1.5 开发规范说明

- 所有服务统一遵循 go-zero 标准目录布局: `etc/` → `internal/config/` → `internal/handler/` → `internal/logic/` → `internal/svc/` → `internal/model/`
- 代码生成使用 `goctl` 工具, 基于 `.api` (REST) 和 `.proto` (gRPC) 定义文件生成脚手架
- 业务逻辑仅编写在 `internal/logic/` 目录, handler 层保持极薄 (仅做参数透传)
- 共享能力统一沉淀到 `pkg/` 目录, 禁止服务间相互引用 internal 包

### 5.2 开发顺序排序

#### 可并行开发组

| 并行组               | 模块                      | 理由                                                                        |
|:-----------------:| ----------------------- | ------------------------------------------------------------------------- |
| **A 组 (Phase 1)** | `tag` + `reply`         | tag 无任何业务依赖, 完全独立; reply 仅依赖已实现的 user/article, 两者互不依赖                     |

#### 强制串行依赖链

```
tag ──────────────────────→ qa (tag 必须先完成)
reply ────────────────────→ message (reply 必须先完成)
reply ────────────────────→ qa (建议 reply 先完成, 非强制)
like/mq (改造) ───────────→ message (like 事件需新增通知投递)
article/mq (改造) ─────────→ concerned (CDC 需新增 collect_num 同步)
message + concerned + qa ──→ member (member 的到期通知依赖 message)
```

| Phase 2 | message   | 3-4 天  | 站内通知中心上线             |
| Phase 2 | concerned | 2-3 天  | 收藏功能上线               |
| Phase 3 | qa        | 5-7 天  | 问答功能上线               |
| Phase 3 | chat      | 7-10 天 | 即时通讯上线 (含 WebSocket) |
| Phase 4 | member    | 4-5 天  | 会员体系上线               |
| Phase 5 | 优化收尾      | 5-7 天  | 稳定性达标                |

**总计**: 约 31-43 个工作日 (1.5-2 个月), 按并行组压缩后约 **1-1.5 个月**。

## 6. 风险点与开发注意事项

### 6.1 架构层面

| 风险点              | 影响                                              | 避坑建议                                                              |
| ---------------- | ----------------------------------------------- | ----------------------------------------------------------------- |
| **服务端口冲突**       | `user/rpc` 和 `like/rpc` 目前均配置监听 `:8080`, 部署时会冲突 | 建立全局端口分配规范文档, 每个服务独占端口, 在上线前逐服务核查                                 |
| **数据库单点**        | 所有 MySQL 部署在同一实例 `101.42.34.232:3306`, 宕机影响全站   | 短期: 配置主从复制 + 读写分离; 长期: 核心服务 (user/article) 使用独立实例                 |
| **Canal CDC 单点** | Canal 故障导致 ES 索引/计数同步中断                         | 配置 Canal 集群模式, Kafka 消费者做好断点续传与幂等处理                               |
| **Kafka 消息积压**   | 突发流量导致消息积压, like/reply 操作延迟可见                   | MQ 消费者设置合理的并发数 (goroutine 池), 配置消费延迟监控告警                          |
| **Redis 缓存雪崩**   | 大量缓存同时过期, 请求直接打到 MySQL                          | 缓存 TTL 加随机偏移 (TTL ± 30%), 使用 singleflight 防击穿 (article/rpc 已有此模式) |

### 6.2 模块层面

| 模块          | 风险点                                   | 避坑建议                                                 |
| ----------- | ------------------------------------- | ---------------------------------------------------- |
| **reply**   | 嵌套评论层级过深导致查询性能差                       | 限制最大嵌套深度 3 层, 超出折叠展示; 查询使用递归 CTE 或逐层加载               |
| **reply**   | CDC 同步 comment_num 时 Canal 消息乱序导致计数不准 | 消费者侧基于 binlog 时间戳做幂等, 定期全量对账修正                       |
| **tag**     | 大量文章共用同一标签, tag_resource 表数据膨胀        | 对高频标签的关联查询直接走 Redis 缓存, 不做 JOIN 查询                   |
| **chat**    | WebSocket 连接数过万, 内存/文件描述符压力           | 单节点 WebSocket 上限建议 50k, 超出需做水平扩展 + 连接路由; 使用 epoll 优化 |
| **chat**    | 消息丢失 (WebSocket 断连时消息未送达)             | 消息先写 Kafka 再推 WS, 客户端重连后拉取离线消息; 不依赖 WS 确认作为消息持久化依据   |
| **message** | 通知生成过多, 用户骚扰                          | 聚合策略: 同类通知合并 (如 "5 人赞了你"); 提供通知偏好设置接口                |
| **message** | 通知表数据量增长过快                            | 按月份分表, 保留 30 天热数据, 超期归档到冷存储或删除                       |
| **qa**      | 回答中 Markdown 内容 XSS 风险                | 服务端存储时做 HTML 标签白名单过滤, 前端渲染时使用 DOMPurify 或类似库         |
| **member**  | 支付回调幂等处理不当导致重复开通/扣款                   | 以支付渠道回调中的 transaction_id 为幂等键, 数据库建立唯一索引             |
| **member**  | 到期降级延迟导致用户仍享受会员权益                     | Redis key 过期事件 + 定时任务双保险, 权益校验侧也需检查 expire_time      |

### 6.3 开发流程层面

| 建议                        | 说明                                                                      |
| ------------------------- | ----------------------------------------------------------------------- |
| **先设计 Proto/API 契约, 再编码** | 服务间通过 `.proto` / `.api` 文件对齐接口, 接口定义先行, 实现后行                            |
| **新服务必须接入可观测性**           | 使用 `pkg/orm` 和 `pkg/es` 即可自动获得追踪+指标; 新服务在配置中必须包含 Prometheus 和 Jaeger 端点 |
| **每个服务独立 go-test**        | 不依赖集成环境, 核心 Logic 用 Mock RPC Client 进行单元测试, 数据访问层用 testify/mock 隔离      |
| **上线前做一次全链路压测**           | 以 wrk / vegeta 工具对核心 API 做阶梯加压, 记录 QPS 上限和资源消耗曲线, 明确扩容阈值                |
| **数据库变更用 Migration 管理**   | 不要手动改 DDL, 使用 golang-migrate 或 goose 管理 SQL 版本文件, 可回滚                   |
